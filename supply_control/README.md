# HackAlem AI: replenishment calculation core

Детерминированное ядро расчёта заказов поставщикам для кейса ТОО «Электрокомплект».
Исходные Excel-файлы читаются без изменений. LLM не участвует в числовом расчёте и может
использоваться только для объяснения уже рассчитанного результата.

## Что реализовано

- очистка транзакций с раздельным учётом продаж, возвратов, итоговых и некорректных строк;
- выявление разовых крупных заказов на уровне документа и клиента;
- исключение незавершённого текущего месяца;
- явная компенсация спроса только при наличии количества дней stockout;
- классификация спроса по ADI/CV²;
- простой champion-прогноз по последнему полному месяцу; challenger-модели доступны
  только в экспериментальном режиме и включаются при улучшении ошибки минимум на 5%;
- учёт сезонности, роста и категории через отдельные множители;
- расчёт целевого запаса, свободного остатка и товара в пути внутри горизонта;
- округление заказа вверх до MOQ;
- группировка по поставщику и детерминированное объяснение каждой строки;
- блокировка результата при отсутствии обязательных параметров.

## Формула

```text
cover_days = lead_time_days + review_period_days
target_stock = daily_forecast * (cover_days + safety_stock_days)
net_need = max(0, target_stock - (on_hand - reserved) - eligible_inbound)
order_qty = ceil(net_need / MOQ) * MOQ
```

Товар в пути учитывается только при ETA не позднее конца горизонта покрытия. Если он
приходит после прогнозной даты дефицита, позиция дополнительно требует ручной проверки.

## Почему реальные заказы пока заблокированы

В переданных файлах нет надёжного справочника сроков поставки и политики страхового
запаса. Нет явных stockout-периодов и обезличенного клиента. Поэтому ядро рассчитывает
прогнозные признаки, но не маскирует отсутствующие параметры нулём и не выпускает
производственный заказ.

Поля `Кэф. Роста` и `Кэф. Сез-ти` загружаются как исходные признаки, но не применяются
автоматически: сначала нужно подтвердить их бизнес-определение. Иначе коэффициент роста
`-0.408` можно ошибочно принять за готовый множитель.

Переключатель `allow_challengers` по умолчанию выключен. На переданном наборе автоматический
выбор модели по отдельному SKU переобучался и проигрывал простому прогнозу на отложенном
периоде. Сезонность можно передать явно через проверенные помесячные индексы.

## Проверка

```bash
python3 -m unittest discover -s tests -t . -v
python3 scripts/audit_replenishment_core.py
```

Аудит реального файла создаёт `data/analysis/replenishment_core_audit_systeme.json`.

## Демо-сценарий

Настройки `config/demo_systeme_assumptions.json` отделены от подтверждённых исходных
данных. Они позволяют показать жюри полный расчёт, но не являются основанием для реального
заказа поставщику.

```bash
python3 scripts/generate_demo_recommendations.py
```

Результат сохраняется в `outputs/demo/systeme_recommendations_demo.json` и краткий отчёт
`outputs/demo/systeme_recommendations_demo.md`. Каждая незаблокированная строка остаётся
в статусе ручной проверки.

## Интерфейс MVP

Статический dashboard находится в `site/dist`. Он открывает рабочую очередь из 497 SKU,
поддерживает поиск, фильтры, просмотр обоснования, локальное подтверждение менеджером и
CSV-экспорт подтверждённых строк. Автоматической отправки заказа поставщику нет.

```bash
python3 site/scripts/build_data.py
python3 -m http.server 4173 --directory site/dist
```

После запуска откройте `http://127.0.0.1:4173/`.
